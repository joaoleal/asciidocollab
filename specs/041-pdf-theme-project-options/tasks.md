- [X] T077 [US3] Add `paragraph-numbering.placement: margin` — numbers beside the text rather than inside it, the way a critical edition or a legal document sets them. Contributes `paragraph-numbering.placement` and `paragraph-numbering.gap`. **`margin` is the default.** It is layout-neutral: it draws into a `float`, and a margin-numbered document paginates identically to the same document with the extension switched off (verified against an unnumbered baseline render, page for page). - [X] T078 [US3] **Correction to the record.** Margin placement was briefly reported as costing an extra page and stranding a number, and the default was reverted on that basis. That diagnosis was wrong: it compared margin against INLINE, which is not a valid baseline. Inline adds text to the flow, and the added prefix changed a multi-column region's measured height enough to flip `single_page?` and switch column balancing ON — so inline rendered the stress document in 3 pages where the UNNUMBERED document takes 4. Margin matches the unnumbered baseline exactly (same extents, same page count), in both the old and the simplified code. The default is `margin` again.
- [X] T079 [US3] Balance the final page of a multi-column region (FR-031c follow-up). **The scope was wider than first recorded:** the old `_asciidocollab_balanced_height` gave up unless the region fitted a single COLUMN, not a single page, so every region taller than one column stayed ragged whether or not it spanned pages. Measured on the shipping engine, the last page of a 26-paragraph region came out `573.2 / 0` at two columns and `671.6 / 0 / 0` at three — the trailing columns were entirely blank, so a tall region read as though it stopped being columnised exactly where it ends.
  **Why one `column_box` can express it after all.** The earlier note said the region would have to be split. It does not: `ColumnBox#reset_top` restores the full page height on every new page, so the final page's height can simply be installed as that page is entered. A `BalancedFinalPage` module prepended to `Prawn::Document::ColumnBox` does exactly that, keyed on a count of page transitions rather than an absolute page number so it is immune to pagination drift. It clears itself on `single_file`, because `dry_run` dups the live bounds and content nested in the region would otherwise balance its own measuring pass.
  **Three things the measurement had to get right**, each found by rendering and measuring rather than by reading:
  1. *`dry_run` cannot be used for this.* It narrows its copy of the bounds to one column (`single_file`), which measures total height correctly but destroys what balancing needs — which column the content stopped in, and on which page. The region is flowed through a REAL column box in the scratch document instead.
  2. *The scratch document carries its own font state.* Left unsynced it measured the region in whatever face the scratch was last used with and reported an end position the real render never reaches — the columns balanced against a document that does not exist. This was the difference between visibly uneven columns and level ones; `dry_run` syncs the same four values for the same reason.
  3. *One pass overstates the content.* A column is abandoned as soon as the next paragraph will not fit, so a full column is not a full column's worth of text and the dead space below the break is counted as content. Re-measuring at the candidate height shrinks it; the plan is iterated to a fixpoint (`REFINEMENTS = 3`) and each candidate is adopted only after it is shown to paginate exactly as the natural flow did — an extra page is a far worse regression than a ragged foot, and is the failure this feature already shipped once.
  **Result**, same documents, same engine: `272.7 / 272.7` at two columns and `229.1 / 213.4 / 185.6` at three, each also one page shorter than the natural flow. Pinned by a new invariant in `column-layout.integration.test.ts` requiring every column of every region page to reach 60% of its deepest column; verified to fail (and only it) with the plan disabled. Both affected parity references were regenerated.
  **Placement rule:** the rightmost column's numbers go in the right-hand margin, every other column's on the left. A two-column region therefore reads outward, one number in each page margin and nothing in the gutter. An INTERIOR column (only reachable at three or four columns) has just the 12pt gutter to work with, which cannot hold a number, so those paragraphs fall back to numbering inline — measured, not assumed, so a theme that widens `page.column-gap` gets margin numbers there too.
  **Three things the upstream recipe gets wrong**, all found by probing rather than reading, and all fixed here:
  1. *The number is drawn before the converter has decided where the text goes.* A paragraph pushed to the next page leaves its number stranded at the foot of the previous one — upstream emits `cannot fit formatted text on page` and renders that paragraph with NO number, so the sequence skips. No pre-check can predict this, because the rule that moves the paragraph is orphan control, not "does one line fit". Settled instead the way the converter settles any other block: convert once into a scratch document, then `position_onto` the real one.
  2. *`Prawn::Document::ColumnBox#right_side` is unusable.* It derives from `absolute_right`, and `ColumnBox` redefines `width` to mean ONE COLUMN, so `absolute_right` is already the first column's right edge and subtracting the remaining columns walks off the page — it reports **-134** for the first column of a three-column box. The edge is computed from `left_side + width` instead.
  3. *A position expressed relative to the bounds is column-blind.* `bounds.absolute_left` is the left of the whole box, so upstream's `[-label_width, cursor]` puts every column's numbers in the same page margin, stacked over one another. Positions are computed absolutely and converted.
  The measuring pass needs the same footnote/counter guard as `multi-column-sections` (4 below), for the same reason. Pinned by `extension-paragraph-numbering-margin`, which covers all three column cases and the page break.
- [X] T080 [US3] **Paragraph numbering broke column balance wherever it fell back to inline.** Under margin placement the measuring pass returned early for EVERY paragraph (`return super if scratch?`) on the grounds that a margin number is out of flow and must not be measured. True — but only when the number actually reaches the margin. When the slot is too narrow the real pass inks the number INLINE, which is in the flow, so the measurement was short by one prefix per paragraph and the balancer divided a total that did not exist. Pinned instead by a third case in `column-layout.integration.test.ts` (three columns WITH numbering, since an interior column's gutter cannot hold a number), verified to fail — and only it — with the fix reverted.

- [X] T054 [P] [US3] Implement the **additional contents entries** extension — **scope decided: separate List of Figures and List of Tables pages** (not figures interleaved into the main contents). `data-model.md` left this entry's Notes cell empty, so the scope was an open question; separate lists are the publishing convention and what the entry is useful for.
      — **Follow-up: the entries had no dot leaders.** The first version floated a right-aligned page number beside each caption, which read as a visibly different kind of list sitting next to the contents — and, worse, ignored the `toc.dot-leader.*` theme keys an author had already set. The entry layout now mirrors `ink_toc_level` exactly: same page-number placeholder width (`toc-max-pagenum-digits`, so the columns line up), the same fragment-position walk to find where a wrapped caption's LAST line ends, and the same leader built from the same theme settings — including honouring `toc.dot-leader.content: ''` to switch leaders off. One set of theme keys now styles all three lists.
      — **Follow-up: entries were not clickable, and front-matter page numbers were wrong.** Two defects with the same root cause — approximating `ink_toc_level` instead of matching it.
        * *No link destinations.* A contents entry is clickable because every section has an id, so the converter registers a PDF destination for it. Image and table blocks get an id only when an author writes `[[figure-1]]`, and `convert_image`/`convert_table` both guard their `add_dest_for_block` call on `node.id` — so an ordinary captioned figure had nothing to link to. The extension now assigns a namespaced id before `super`, letting the converter's own machinery place the destination with the geometry it uses for any other anchored block. The id is a document-order counter, not `object_id`, because a PDF must be byte-reproducible. Verified by reading the annotations back out: caption AND page number are both live, and a caption wrapping onto three lines gets a link rect on each.
        * *Front-matter pages cited a number that appears nowhere in the book.* When a page falls before the numbering start, the contents list prints a lowercase Roman numeral of its physical position; this printed the physical Arabic number instead. Invisible in any document whose numbering starts at page 1, which is every fixture that existed. Where numbering starts is configurable (`page.numbering.start-at`: cover, title, toc, after-toc, body, or an explicit number) and also depends on the doctype, whether there is a title page or front cover, and where the contents sit — so the count is taken from the converter's own `num_front_matter_pages`, handed down through `ink_toc`, rather than recomputed. `extension-additional-contents-entries-front-matter` pins it: under `start-at: 3`, every label in the list now matches that page's own printed folio (v, vi, 1, 2).
- [X] T055 [P] [US3] Implement the **title-block document details** extension — **scope narrowed by T074.** Interpolating arbitrary attributes into the title block is already native (`title-page.authors.content.*` is attribute-substituted with `drop_lines_with_unresolved_attributes`), so that part ships as a theme setting. Only multi-line LAYOUT is not reachable — `ink_prose` normalizes whitespace and collapses any multi-line template onto one line. The extension does that and nothing more.

- [X] T059 [US3] Implement the preview comparison toggle in `apps/web/src/components/theme-editor/extension-comparison-toggle.tsx` — select one enabled extension, switch the preview between with and without it, changing nothing else (FR-031b1, FR-031b2), absent or plainly unavailable when no extensions are enabled (FR-031b3)
      — Building it exposed that the whole browser half of the extension load path was **unwired**. T037 (registry) and T038 (the `require` seam) were both built and tested, and the two ends — the API's catalogue/source routes and the Ruby `require` — worked; but nothing connected them. `resolvePdfExtensions` had exactly one non-test caller, the parity harness. So no render in the application had ever loaded an extension, and a comparison toggle over that would have compared two identical documents. Wired end to end: `getSource` client method → `usePdfExtensionBundle` → `RenderRequest.extensions` (on the request, not worker state, so a render posted before a separate "here are the extensions" message could never render silently without them) → `mountPdfExtensions` in the worker → `extensionPaths`. The snapshot builder now carries the project's selection, so the export and the preview render the same thing.
      — The second finding is the one that decides the design: **`Module#prepend` cannot be undone, and the wasm VM is warm and never torn down.** An extension required into it stays in effect for every later render in that session, which makes SC-015a (disable → back to unextended output) and FR-031b1 (preview *without* one extension) both unsatisfiable on their own terms. Growing the set is free; shrinking it discards the VM and builds a fresh one over the already-compiled module (`needsFreshVm`). Without that the toggle would have appeared to work while showing the same document twice.
      — A refusal now rides out as an `extension-not-loaded` diagnostic rather than a console line: an extension the project enabled that did not load changes the document, and an author told nothing would read the result as correct.
- [X] T060 [US3] Implement inert targeting markup so a document carrying markup for a disabled extension renders exactly as if the markup were absent, with no error and no stray output (FR-031a2)
      — Verified against the real toolchain, not asserted: the theme-editor sample (which carries every shipped extension's targeting markup) was rendered with NO extensions loaded, and again with all the markup stripped out. **Same page count, and the extracted text differs by exactly one line.** Every document attribute and every `[.role]` is completely invisible when its extension is off.
      — The single difference is `[colophon]`, and it is a deliberate exception rather than a gap. `[colophon]` is standard AsciiDoc, not something this catalogue invented — the base converter already renders it, as an ordinary numbered chapter, and `colophon-placement` changes where it goes rather than whether it appears. So with the extension off it reads "Chapter 11. Colophon" instead of an unnumbered "Colophon" at the back. Degrading to the meaning AsciiDoc already gives the markup is a better outcome than invisibility, so it is pinned by a named test rather than "fixed".
      — `apps/api/tests/shipped-pdf-extensions.test.ts` holds the set-level invariants this proved: every targeting string is one of the three inert forms, source and manifest exist for each other, ids are unique and sorted, and no contributed theme key shadows a built-in or another extension's.
- [X] T061 [US3] Ensure newly added extensions default to disabled for every existing project, so adding one never changes existing output (FR-032g, FR-036, SC-012b, SC-015) — **the property already held; nothing pinned it.** Audited the whole chain and found opt-in at every step: `extensions.enabled` is optional in the schema, `resolveRenderConfig` never touches extensions, `buildProjectSnapshot` OMITS the field when the selection is empty, `requestedExtensionIds` maps `undefined` to `[]`, `resolvePdfExtensions` iterates only the ids it is given, and both the settings UI (`draft.extensions?.enabled ?? []`) and the theme editor (`NO_EXTENSIONS`) default to none.

  The one place the opposite convention is real: the Ruby convert treats a **nil** enabled-set as "everything loaded is active" — the canonical `asciidoctor-pdf -r` contract, and how parity references are produced. What keeps that from meaning "all extensions on" is that nothing is ever loaded in the first place, which is a property of the layers above it rather than of the convert.

  Pinned at three layers, because a regression in any one of them alone would be silent: the schema (a config carrying no `extensions` key normalises to `undefined`), the snapshot builder (empty selection ⇒ field omitted, and a real selection still passes through, so the test cannot be satisfied by dropping the field unconditionally), and the mount (a request from a pre-feature project loads nothing, rejects nothing and writes nothing even when the deployment offers ready-to-load extensions — plus that absent and empty resolve identically, so projects created before the feature behave exactly like projects created after it that enabled nothing).
- [X] T062 [US3] Add an e2e test in `apps/web/e2e/pdf-extensions.spec.ts` — **and it found a real defect on its first run.** Five tests: enable → visible effect (the licence page is a whole extra page) → disable → SHA-256 identical to the unextended export; every shipped extension enabled at once, then the same set stored in reverse order producing identical bytes; and three administrator-folder tests (a dropped extension appears with no rebuild, a malformed one is excluded *with a reason* while a valid one beside it still loads, a colliding id is reported as a conflict and offered exactly once).

  The stack scripts now point the API at a writable per-run drop folder with a 1s scan cache — the production default `/data/pdf-extensions` does not exist locally and a MISSING folder is deliberately the "no extensions offered" case, so without this the administrator flow would have passed while testing nothing.

  **The defect: an export taken before its configuration arrived rendered the wrong document, silently.** The order-independence test failed on its first attempt and passed on retry — the signature of a readiness race, not an order bug. `useProjectRenderConfig` exposes `loading` and the editor layout discarded it, and `usePdfExtensionBundle` returns an empty bundle until the Ruby sources arrive. Either window produces a perfectly good PDF that is missing the project's theme, page size and extensions; the registry's "no source was supplied" rejection is reported, but the download already happened. A live preview re-renders and heals; a downloaded file does not. Fixed by exposing `ready` from the bundle hook and gating the export button on `!renderConfigLoading && projectExtensionsReady`. Readiness settles on FAILURE too — a fetch that never succeeds must not disable the control for ever.

  Verified by re-running: 7 passed, 0 flaky (was 6 passed + 1 flaky). Pinned by 7 unit tests on the hook, counterfactually checked — stubbing `ready: true` fails 4 of them.

## Implementation Strategy

### MVP

Phase 1 + Phase 2 + Phase 3 (US1). Delivers a sectioned options page and — via T005/T006 — fixes the

1. **Setup + Foundational** → theme content reaches the renderer; parity runs in CI

Each step leaves the application releasable.
